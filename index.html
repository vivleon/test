04-B. App Suite Expansion 학부모앱 확장 + 교사앱 + 버스(기사)앱 + 관리자/관제

Scholix는 현장 운영을 역할 기반(Role-Based)으로 분리하여, 각각의 앱이 “최소 입력”으로 동일한 원천 로그를 생성하도록 설계합니다. 즉, Teacher(교사)와 Driver(기사)는 태깅/예외를 만들고, Admin(관리자)는 승인/배포/감사를 수행하며, Parent(학부모)는 알림/서류 제출에 집중합니다. 본 섹션은 “화면 목업 + 로직 고려”를 함께 포함합니다.

07. Product Specification Teacher/Driver/Admin/Parent Suite 상세 기획 (부록)

A) Teacher App 상세 기능 Core
  • Gate-Out 체크: NFC/QR 스캔 또는 리스트 터치(Manual Fallback), 반(클래스) 단위 일괄 처리
  • 예외 처리: 태그 분실/대리 인계/조기 귀가/보호자 직접 픽업(사유 필수)
  • AI 문서화: 사고/상담/투약/안전일지 음성 입력 → Draft 생성 → 교사 검수 → 확정
  • 민원/서류 승인: 투약/결석/귀가동의서 워크플로우(반려/수정요청/승인)
  • NEIS 대응: ‘연동형’ 출력(표준 서식/CSV/PDF) + 업로드 체크리스트
  • 알림 운영: 위험 알림(Severity High)은 Teacher ACK 의무 + 처리 코멘트
* MVP 우선순위: Gate-Out + 예외처리 + 위험 ACK + 민원 승인
B) Driver App 상세 기능 Mobility
  • 노선 시작 전 정합성: Gate-Out 완료자 목록과 대조, 미탑승 있으면 출발 Soft-Lock
  • Boarding/Drop-off 태깅: 스캔 + 음성/버튼(수동) + 오프라인 큐
  • 운행일지 자동: 출발/도착/정차/예외 이벤트로 일지 생성(기사 부담 최소화)
  • 안전 체크: 노선 종료 시 Drop-off 미완료자 0명 될 때까지 종료 제한(운영 정책)
  • 지연 브로드캐스트: ETA 업데이트(계산값) + 학부모 “정보(Info)” 알림
* 무설치 운영: 스마트폰 + NFC 스티커(또는 QR) 기준
C) Admin Console 상세 기능 Console
  • RBAC: 원장/행정/담임/보조/기사 역할별 메뉴 접근 제어
  • 대시보드: 실시간 운행 현황(지도), 출석률, 미처리 민원, 안전사고 요약
  • 감사 로그: 모든 데이터 변경 이력(Who/When/What/Why) 보관 및 검색
  • 설정: 학급 관리, 원아 대장(일괄 업로드), 버스 노선 편집, 알림 정책 설정
D) Parent App 상세 기능 Touchpoint
  • 안심 알림: 등/하원, 승/하차, 도착 예정(지연 시), 공지사항 푸시
  • 간편 서류: 투약 의뢰서(사진 첨부), 결석계, 귀가 동의서, 방과후 신청
  • 셔틀 위치: 내 아이가 탄 버스의 실시간 위치 조회 (운행 중에만 활성)
  • 앨범/소식: 반별 앨범, 식단표, 가정통신문 확인 (기존 키즈노트 대체 가능)

08. Pre-flight Checklist 파일럿 도입 전 필수 확인 사항

🚀 1주차: 환경 분석 및 준비 (Onboarding)

  • ✅ 인터넷 환경 점검: 교실/현관/버스 내 WiFi 또는 LTE/5G 신호 강도 측정 (음영지역 확인)
  • ✅ 기기 확보: 교사 개인폰 활용 동의 여부 또는 공용 태블릿 지급 계획 수립
  • ✅ 데이터 이관: 기존 원아 명부(엑셀) 정비 (반/이름/보호자연락처/버스노선 필수)
  • ✅ NFC 태그 부착: 원아 가방 및 네임택에 태그 부착 및 매칭 테스트

🚌 2주차: 모의 운행 (Dry Run)

  • ✅ 기사님 교육: 앱 설치, 로그인, 운행 시작/종료, 태깅 방법 실습 (1:1 교육 권장)
  • ✅ 데이터 정합성 테스트: 가상 등하원 시나리오 수행 (정상/미탑승/미하차 등 예외 케이스 포함)
  • ✅ 알림 테스트: 관리자/교사/학부모(테스터) 계정으로 알림 수신 여부 확인

🏁 3주차: 실전 운영 (Go Live)

  • ✅ 학부모 안내: 앱 설치 안내문 배포, 가입 승인 처리
  • ✅ 헬프데스크 운영: 초기 문의 대응을 위한 핫라인(카카오톡 채널 등) 가동
  • ✅ 일일 모니터링: 첫 1주일간 매일 로그 분석 및 이슈 리포트 작성

Offline Queue & Idempotency Reliability

Client-side algorithm (pseudo)

enqueue(event):
  event.eventId = ULID()
  event.idempotencyKey = hash(deviceId + event.eventId)
  persist(localQueue, event)

sync():
  for event in localQueue order by occurredAt:
    resp = POST /transit/events with Idempotency-Key
    if resp.ok:
      mark(event, "SENT") and remove from queue
    else if transient:
      retry with backoff
    else:
      mark(event, "FAILED")
      show operator action (Driver/Teacher)

server_receive(event):
  if exists(orgId, idempotencyKey):
    return 200 (idempotent)
  
  validate(role, event.type)
  write TransitEvent
  run reconciliation rules -> maybe create Alert
  write AuditLog
  return 200
* 오프라인 구간이 잦은 환경을 전제로 “신뢰성(Resilience)”을 KPI로 관리
